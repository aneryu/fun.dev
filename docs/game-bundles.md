# fun.dev game bundles — API v2

fun.dev owns the page and the Three.js runtime. A game delivers an ES module and
its assets. It does not create an HTML document, renderer, or animation loop.
The lobby (`/games`) and the player (one page per game at `/games/<id>`) are shared across all games.
The same bundle also runs on `fun`, the native runtime; what each host provides is in
[hosts](hosts.md).

Apart from Three.js and this container API, games must be self-contained. Keep
game resources, UI copy, development tools and tests within their bundle.
Do not import platform application modules or rely on its CSS variables, global
resets, DOM IDs, catalog, router, storage or services. Draw game visuals and HUD
in Three.js; games do not create HTML interfaces or ship CSS. The platform renders
only what games declare as data: `howToPlay` text and the options panel. It
offers optional gameplay helpers (the runtime kit) through `context.runtime()`.
Resolve game resources through `asset()`.
A game's source directory can therefore be copied and tested independently; only
the foundation host needs replacing.

Files under a `lazy/` directory (for example `assets/lazy/`) are published like any
other runtime file, but the service worker does not download them when the game is
first opened; they are cached the first time the game requests them. Use it for
large optional downloads, such as a model needed only by one feature.

Optional `dev/`, `package.json` and `README.md` files at a bundle's root hold
development tooling and documentation. Builds and the publisher copy only the
runtime files listed in `game.json`; runtime code must never reference others.

## Bundle layout

Game sources live in the private `fundev-games` repository, checked out beside the
platform (`FUNDEV_GAMES`, else `../fundev-games`), one directory per game at its root,
without a copy per version. The version is the `version` field of its `game.json` manifest;
history is kept by Git and the immutable R2 releases.

```text
my-game/
  game.json           # catalog metadata and the runtime file list
  game.js             # ESM entry: export createGame(context)
  assets/             # optional textures, models, audio, etc.
  chunks/             # optional relative ESM imports
  dev/                # optional tooling and tests, never published
  assets.lock         # records assets/, which is not in Git
  models.lock         # optional: pinned library models
```

The directory name must match the manifest `id`. The public registry is R2's
`games.json`, updated by the independent publisher described in
[game registration](game-registry.md). Local builds generate their catalog from
each `<id>/game.json` in the games directory, sorted by ID, without the `files` list. In the public
registry, array order is display order and entries additionally include a
`release` content hash generated by the publisher:

```json
[
  {
    "id": "my-game",
    "version": "1.0.0",
    "apiVersion": 3,
    "title": { "zh": "我的小游戏", "en": "My game" },
    "description": { "zh": "一句话说明玩法。", "en": "A short description." },
    "category": { "zh": "益智", "en": "Puzzle" },
    "platforms": ["mobile", "desktop"],
    "orientation": "landscape",
    "howToPlay": { "zh": "左摇杆移动，右键跳。", "en": "Left stick moves, right button jumps." },
    "cover": "assets/cover.jpg",
    "keepAwake": false
  }
]
```

IDs use lowercase ASCII letters, numbers, and single hyphens. Versions use
`major.minor.patch`. `platforms` lists devices the game actually supports: do
not mark a keyboard-only game as mobile. The catalog only lists ready games;
an empty array is valid. Duplicate IDs fail validation. The platform runs exactly
one API version: the lobby hides entries for another version, and the player
explains them (“fun.dev has been updated” or “this game is being updated”). The
publisher accepts only the current version. All games upgrade with the platform.

Optional fields:

- `orientation`: `any` (default), `portrait`, or `landscape`. On phones the player
  pauses with a rotate prompt until the device matches, and fullscreen tries to
  lock the orientation where browsers allow it (Android).
- `howToPlay`: text or `{ zh, en }`, shown at the top of the player's Options.
- `cover`: a 1200×630 `.jpg`, `.png` or `.webp` inside the bundle and listed in
  `files`. The lobby shows it as a square thumbnail; share cards use it whole.
- `keepAwake`: hold a screen wake lock while running (idle or watch-style games).
- `models`: library models pinned by version, `{ "desk_chair_01": "v002" }`, served at
  `models/<id>.glb` — or, with `"modelFormat": "fun3d"`, at `models/<id>@<version>.fun3d` in
  fun.dev's own format, batched and simulated by the runtime kit ([models](models.md),
  [model format](model-format.md)); the build writes `models.lock`, commit it.
- `convert`: patterns of bundled GLB files to derive to `.fun3d` at build, as strings
  (`"assets/props/*.glb"`, converted as props) or `{ "files": "assets/tiles/**/*.glb",
  "type": "piece" }` (`prop`, `piece`, `vehicle`, `character` decide the physics the profile
  derives). Each matched file gets a `.fun3d` beside it (`assets/props/tree.fun3d`), served as
  a blob with the release and loaded with `context.asset(path)`; derivation runs once per
  source and converter and is cached locally.
- `recording`: offer **Record video** in the player menu. The player records the game
  canvas (including the Three.js HUD, never platform controls) with the session's sound,
  even when muted, as a 720×1280 portrait clip for short-video apps, up to 60 seconds. The
  frame keeps the canvas's full width (wider, desktop canvases: a 3:4 slice) and centres the
  game's focus vertically; where it reaches past the top or bottom, the edge rows are
  stretched, so a plain background or a cut-off body continues. A watermark with the game
  title and `fun.dev/games/<id>` sits at the top left. Recording pauses with the game. The clip is MP4 where the browser can encode it
  (Safari, recent Chrome), otherwise WebM, and stays on the device unless the player
  shares or saves it. Games need no code for it; two optional hooks refine it:
  `recordingFocus()` returns `{ x, y }` in viewport pixels to centre in the video (for
  example a face), and `recordingBadge()` returns an image (canvas, `ImageBitmap`, …) or `null`, shown
  in a small ink frame at the top left with the watermark beside it (for example a photo the player chose).

`title`, `description`, and `category` accept either a shared string (e.g. `Demo`)
or an object containing both `zh` and `en` translations. Search matches both
languages.

The player resolves the entry to `/games/<id>/<version>/game.js`. Asset paths
are relative to this bundle, never to the game page's URL. Keep published
version directories immutable and bump `version` when changing code or assets.

Files under `assets/` are published as content-addressed blobs shared across
versions and games (see [assets](assets.md)), so always load them through
`asset()`. They must not reference each other by relative path (export `.glb`,
not `.gltf` with side files), and modules cannot import from `assets/`
statically; the publisher rejects both. In the games repository `assets/` is not in
Git: `npm run assets` records it in `<id>/assets.lock`.

## Game interface

```js
export const options = []; // optional, see “Options panel”

export function createGame(context) {
  // Set up the scene and input. This function may also be async.
  return {
    update(delta, elapsed) {},
    resize({ width, height, pixelRatio, safeArea }) {},
    pause() {},
    resume() {},
    localeChanged(locale) {},
    optionChanged(id, value) {},
    shareText(locale) { return "…"; },
    recordingFocus() { return { x, y }; }, // see manifest `recording`
    recordingBadge() { return null; },
    dispose() {},
  };
}
```

`createGame` must return an object. All hooks are optional, synchronous methods.
An optional `snapshot()` returns JSON-compatible application diagnostics (state,
time, selected action, resource counts). The fun adapter exposes it through the
local `game.inspect` RPC; an absent hook returns `null`. It is a readback, not a
save format or a claim of rendered pixels. Keep it bounded and free of secrets.
The module's top level must not start gameplay or allocate per-session resources:
ES modules are cached; restarting calls `createGame` again with a fresh context.

| Context | Ownership and behavior |
| --- | --- |
| `apiVersion` | Currently `3` (API v3: the WebGPU renderer and node materials). |
| `locale` | Live `zh` or `en` getter. Read to select game UI text. |
| `THREE` | Platform's shared Three.js module, the WebGPU build (`three/webgpu`) pinned to `0.186.1`. TSL is `THREE.TSL`. |
| `scene` | Fresh scene owned by the container. Add game objects here. |
| `camera` | Default perspective camera at `(0, 0, 5)`, looking toward the origin. |
| `setCamera(camera)` | Replace the active camera, e.g. with an orthographic camera for a 2D game. |
| `renderer` | Shared host `THREE.WebGPURenderer` for this session, already initialised: WebGPU where the browser offers a hardware adapter, otherwise its WebGL 2 backend. Configure as needed; do not dispose it or replace its loop. See [Rendering](#rendering). |
| `graphics` | `{ backend, tier }`: `"webgpu"` or `"webgl"`, and `"low"` (phones and compact screens: low-power GPU, DPR cap 1.5) or `"high"` (desktop: high-performance GPU, DPR cap 2). Scale optional effects with `tier`. |
| `setRenderPipeline(pipeline)` | Draw each frame with a `THREE.RenderPipeline` (any object with `render()`) instead of `renderer.render(scene, camera)`; `null` restores the plain render. The game owns and tracks the pipeline. `kit/post.js` builds one. |
| `canvas` | Focusable canvas. Bind pointer/keyboard input here; preserve Tab navigation. |
| `viewport` | Live `{ width, height, pixelRatio, safeArea }` values, in CSS pixels; DPR capped at 1.5 on mobile/compact screens and 2 on desktop, and lowered further by `adaptiveResolution`. `safeArea` is `{ top, right, bottom, left }`: display cutouts plus the player's menu button. Keep HUD and controls inside it. Treat as read-only. |
| `invalidate()` | Request a frame for an on-demand game after input or an asynchronous scene change. |
| `asset(path)` | Resolves a path inside this bundle to its URL, e.g. `asset('assets/ball.webp')`; files under `assets/` resolve to their content-addressed blob. |
| `readAsset(path)` | The bytes of a bundle file as a `Uint8Array`, cancelled with `signal`. The runtime kit reads through this, so a game that does too runs on every host ([hosts](hosts.md)). |
| `decodeImage(bytes, { mime, ...options })` | Decodes PNG/JPEG/WebP bytes to a texture source: an `ImageBitmap` on the web (`options` are `createImageBitmap`'s), `{ width, height, data }` pixels on hosts without one. `kit/assets.js` exports `textureFromImage(THREE, image)` for either. |
| `createCanvas2D(width, height)` | A canvas with a 2D context for drawing text or procedural textures: an `OffscreenCanvas` on the web. Pass it to `createText(options, { createCanvas2D })` on hosts without `OffscreenCanvas`. |
| `signal` | Aborted when leaving, restarting, timing out, or failing. Use for fetches and DOM listeners. |
| `track(resource)` | Registers a resource with `dispose()`, returns it, disposes it once at teardown. |
| `onCleanup(fn)` | Registers synchronous cleanup for timers, audio, custom objects, etc. |
| `progress` | Optional v1 local-save capability; see below. |
| `launchReason` | `"open"` or `"restart"`; reset is an explicit player action. |
| `reducedMotion` | User's reduced-motion preference at session creation. Avoid decorative motion when true. |
| `audio` | `{ context, destination }`: the page's shared `AudioContext` and this session's gain node. Connect all game sound to `destination`; never create another `AudioContext`. The host unlocks audio on the first gesture, suspends it while paused, applies the player's mute/volume, and disconnects the session at teardown. Absent if Web Audio is unavailable. |
| `announce(text)` | Screen-reader announcement through the player's live region (up to 200 characters). The player coalesces rapid announcements. |
| `haptics.vibrate(pattern)` | `"tap"`, `"success"`, `"fail"`, or up to 8 durations in ms. Ignored while paused, when the player turned haptics off, or where unsupported (iOS Safari). |
| `pickImage({ maxSize })` | Opens the system image picker (library, camera, files). Call it synchronously from a pointer or key handler; browsers require a user gesture. Resolves an upright `ImageBitmap` whose longer side is at most `maxSize` (default 1024, 16–4096), or `null` when cancelled, paused, already picking, or after the session ends; rejects if the file cannot be decoded. The game owns the bitmap: `close()` it when done. Images never leave the device unless the game sends them. |
| `deviceStorage` | `{ get(key), set(key, blob), delete(key) }` for `Blob` values kept in this browser only, per game: never transferred, exported or synced, unlike `progress`. Keys are 1–32 lowercase letters, digits or hyphens; at most 8 keys of up to 2 MiB each. Use it for data that must stay on the device, such as a picked photo. Absent where IndexedDB is unavailable. |
| `reportLoading(fraction)` | 0–1 progress shown on the loading screen while `createGame` runs. |
| `options` | Read-only live values of the module's `options` (see below). |
| `cheatsUsed` | `true` once any cheat was used in this session. |
| `updateOption(id, changes)` | Adjust an option at runtime: `{ disabled, min, max, value }`. |
| `runtime(name)` | Imports a platform runtime module, e.g. `runtime("kit/text.js")` or `runtime("addons/GLTFLoader.js")`. |

The host calls `localeChanged` and `resize` after creation, then `resume` (or `pause` if hidden),
then `update` before each render. `delta` and `elapsed` are **seconds**; delta
is clamped to 0.05, and elapsed is accumulated simulation time. A resume starts
with delta 0. Hidden tabs and manual pause stop the render loop; becoming visible
does not override a manual pause. The game surface is inert while paused or
loading so its controls cannot take keyboard focus. The host suspends the shared
audio context while paused; `pause`/`resume` must still stop scheduled sounds and
other non-render activity. A resize may draw a still frame while
paused. Orthographic camera bounds belong to the game and should be updated in
`resize`; the host updates perspective camera aspect ratios automatically.

The lifecycle object may also set `adaptiveResolution: true` (continuous games):
when more than half the frames over two seconds miss ~45 fps, the host lowers the
pixel ratio in steps (80%, 65%, 50%) and calls `resize`. It never raises it again
within a session. `?debug=1` shows frame rate, draw calls, triangles, geometry and
texture counts, the pixel ratio, the backend and the tier. `?renderer=webgpu` or
`?renderer=webgl` overrides the automatic backend choice, to compare them on a device.

`localeChanged(locale)` also runs when the player switches languages. Update
game labels without recreating the session or resetting progress. The callback
is optional for existing bundles; the host always translates its own controls.

One frame loop calls `update` and then `renderer.render(scene, camera)`, or the
game's render pipeline (`setRenderPipeline`). Do not start a second loop or call
`renderer.render()` from `update`. Multiple viewports are outside API v3; extend
the contract before adding games that need them.

Games run continuously by default. For games that can rest between interactions,
return `renderMode: "on-demand"`. Call `context.invalidate()` when input changes
the scene, and return `true` from `update` while an animation needs more frames.
Otherwise the host renders that frame and stops until the next invalidation.
Idle time does not advance simulation time. Resize still draws a frame.

Design games for touch first. The mobile player fills the available viewport,
with platform controls in a modal menu that pauses gameplay. Keep HUD controls
clear of the top-left menu and leave generous margins around screen edges.
Verify portrait and landscape, cap geometry and texture costs, and stop work
while paused. Do not require browser fullscreen support to make the game usable.

## Resource cleanup

Register resources **as they are created**, including before an `await`:

```js
export async function createGame({ THREE, scene, track, asset, signal, onCleanup }) {
  const geometry = track(new THREE.BoxGeometry());
  const material = track(new THREE.MeshBasicMaterial({ color: 0xffd43b }));
  const mesh = new THREE.Mesh(geometry, material);
  scene.add(mesh);

  const response = await fetch(asset('assets/level.json'), { signal });
  if (!response.ok) throw new Error('Level unavailable');
  const level = await response.json();
  signal.throwIfAborted();
  // Use level to initialize gameplay.

  return { dispose() { scene.remove(mesh); } };
}
```

At teardown the host stops frames, aborts `signal`, runs `dispose`, then runs
registered cleanups in reverse order, removes the surface, and releases its
renderer. A failing cleanup does not prevent later cleanups. Resources registered
after cancellation are disposed immediately. If async creation finishes late,
its returned `dispose` still runs. Check `signal` after awaits to avoid starting
new activity in a cancelled game. Creation has a 30-second timeout.

`track` geometry, materials, textures, render targets, controls, and skeletons
separately when applicable. Do not also dispose tracked resources in `dispose`.
Use `onCleanup` for untracked timers/listeners and closing `ImageBitmap` objects;
resources removed from a scene are still the game's responsibility. See the
[Three.js disposal guide](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).

Input listeners should use `{ signal }`. Keep game keyboard handling on the
canvas, not global keys that block platform controls. The game owns its HUD
geometry, hit testing, keyboard controls and accessible canvas labels; use
`announce` for changes a screen reader should hear. Camera-attached meshes can
draw screen-space HUD in the same render pass; use depthTest/depthWrite false and
explicit renderOrder for overlay materials (the kit's `createHudLayer` does this).
Do not draw a mute button: sound and haptics switches live in the player's Options.

## Options panel

Games declare settings and cheats as data; the player renders them in **Options**
with native, accessible controls. Export them beside `createGame`:

```js
export const options = [
  { id: "difficulty", section: "settings", type: "choice", default: "normal",
    label: { zh: "难度", en: "Difficulty" },
    choices: [{ value: "easy", label: { zh: "简单", en: "Easy" } }, { value: "normal", label: { zh: "普通", en: "Normal" } }] },
  { id: "sensitivity", section: "settings", type: "range", min: 0.5, max: 2, step: 0.1, default: 1, label: { zh: "灵敏度", en: "Sensitivity" } },
  { id: "lives", section: "cheats", type: "toggle", label: { zh: "无限生命", en: "Infinite lives" } },
  { id: "skip", section: "cheats", type: "action", label: { zh: "跳到下一关", en: "Skip level" } },
  { id: "level", section: "cheats", audience: "debug", type: "range", min: 1, max: 20, label: { zh: "关卡", en: "Level" } },
];
```

- Types: `toggle` (boolean), `range` (`min`/`max`/`step`), `choice` (2–16
  `choices`), and `action` (a button; no value). At most 32 options.
- `settings` persist per game in this browser's `localStorage` (not transferred or
  exported) and are restored before `createGame`; invalid stored values fall back
  to `default`. `cheats` start at their defaults in every session.
- `audience: "debug"` items appear only with `?debug=1`, beside the stats panel.
- Read values from `context.options[id]`; `optionChanged(id, value)` runs after a
  player change (while the game is paused behind the dialog). Actions call
  `optionChanged(id)`. `context.updateOption(id, { disabled, min, max, value })`
  adapts an option to game state, e.g. the highest unlocked level.
- Whether a session that used cheats keeps saving progress is the game's choice;
  `context.cheatsUsed` reports it, e.g. for `shareText`.
- The platform's own switches (mute, volume, haptics) are not game options.

`shareText(locale)` may return up to 280 characters for the player's **Share**
button, e.g. a score. The player appends the game's address `/games/<id>`, whose page
carries the title, description and cover (in Chinese) for link previews.

## Runtime kit

Optional helpers served by the platform with the same Three.js instance, imported
through `context.runtime(name)` so they resolve on the site origin even when the
bundle comes from the game origin. Bundle-relative or absolute `/runtime/` imports
inside a game would resolve against the game origin instead.

| Module | Purpose |
| --- | --- |
| `kit/text.js` | `createText(options, { createCanvas2D })` draws text with system fonts (Chinese and emoji included) into a `CanvasTexture` on a plane or sprite (the second argument is for hosts without `OffscreenCanvas`); `createHudLayer(camera)` maps CSS pixels and safe-area corners onto a camera-attached layer. |
| `kit/input.js` | `createPointer()` (viewport pixels, tap/drag/long press, multi-touch), `createActions()` (keyboard, gamepad and virtual input mapped to named actions), `createVirtualControls()` (on-screen joystick and buttons). |
| `kit/loop.js` | `createFixedStep()` for fixed-step simulation with an interpolation `alpha`. |
| `kit/assets.js` | `createAssets(context)` loads JSON, textures (PNG/JPEG/WebP or KTX2) and glTF/GLB (with Draco, meshopt and KTX2) with cancellation, `track` ownership and `reportLoading`. Textures are decoded with straight alpha, as Three.js expects. Prefer KTX2 for large textures: it stays compressed in GPU memory. |
| `kit/post.js` | `createPost(context, { ao, bloom, grade })`: shared postprocessing scaled to the device tier; see [Postprocessing](#postprocessing). |
| `kit/random.js` | `createRandom(seed)`, `hashString()` and `dailySeed({ timeZone })` (UTC days by default). |
| `kit/vision.js` | MediaPipe Tasks Vision at the platform's pinned version: `load()` imports the library (`FaceLandmarker`, `ImageSegmenter`, …), `fileset` is its wasm, `model(name)` the URL of a platform model (`models`: `face_landmarker`, `hair_segmenter`, `selfie_segmenter`). About 17 MB, downloaded only when used. |
| `addons/GLTFLoader.js`, `DRACOLoader.js`, `KTX2Loader.js`, `MeshoptDecoder.js` | Three.js loaders at the pinned version; decoders at `/runtime/addons/draco/` and `/runtime/addons/basis/`. `MeshoptDecoder` (`EXT_meshopt_compression`, WASM built in) goes to `GLTFLoader.setMeshoptDecoder()`. |

```js
export async function createGame(context) {
  const { createText, createHudLayer } = await context.runtime("kit/text.js");
  const hud = createHudLayer(context.camera);
  context.scene.add(context.camera);
  const score = createText({ text: "0", size: 28, hud: true });
  context.track(score);
  return {
    resize(viewport) { hud.resize(viewport); hud.place(score.object, { x: 24, y: 24 }); },
    dispose() { hud.dispose(); },
  };
}
```

The kit is shared and unversioned: every game upgrades with the platform.

## Rendering

The renderer is `THREE.WebGPURenderer`, so materials are node materials:

- Built-in materials (`MeshStandardMaterial`, `MeshBasicMaterial`, `ShadowMaterial` …)
  work as before; the renderer converts them.
- Custom shading uses TSL node materials (`MeshStandardNodeMaterial` and friends)
  and their slots: `colorNode`, `normalNode` (view space), `roughnessNode`,
  `metalnessNode`, `emissiveNode`, `positionNode` (local space). Start from the
  material's own value (`materialColor`, `materialRoughness` …) to keep its
  parameters live. Uniforms are `uniform(value)` nodes; change `.value` at any time.
- GLSL does not run: `onBeforeCompile`, `ShaderMaterial`, `RawShaderMaterial` and
  `customProgramCacheKey` have no effect or fail. One TSL graph compiles to WGSL for
  WebGPU and GLSL for the WebGL 2 backend.
- Write noise and other shared shader code as `Fn(…).setLayout(…)` so each is one
  shader function instead of being inlined at every call.
- Hash-based noise is not bit-identical between WGSL and GLSL: procedural patterns
  keep their character but may land differently on the two backends.
- `renderer.getMaxAnisotropy()` replaces `renderer.capabilities.getMaxAnisotropy()`;
  `PMREMGenerator`, shadows, `CanvasTexture` and the loaders work unchanged.

Worked examples from abandoned games are on the archive branch `archive/games-2026-10-19`:
`games/muyu/materials.js` (procedural wood and brocade), `games/seal-carving/stone.js`
(texture-driven face with bent normals) and `games/slap/head.js` (an unlit material with
its own vertex deformation).

### Postprocessing

`kit/post.js` builds one `THREE.RenderPipeline` from the scene: ambient occlusion
(GTAO, only on the `"high"` tier unless `ao.everywhere`), bloom (half resolution on
`"low"`) and a light grade (saturation, contrast, tint), then hands it to
`setRenderPipeline`. The scene pass keeps the renderer's antialiasing; tone mapping
and colour space follow `renderer.toneMapping` and the output colour space.

```js
const { createPost } = await context.runtime("kit/post.js");
const post = await createPost(context, { ao: { radius: 0.3 }, bloom: { strength: 0.5, threshold: 0.9 }, grade: { saturation: 1.1 } });
post.bloom.strength.value = 0.8; // effect parameters are node uniforms
```

Custom pipelines use `THREE.RenderPipeline` with `THREE.TSL.pass` and the platform's
postprocessing nodes, `runtime("addons/BloomNode.js")` and
`runtime("addons/GTAONode.js")`.

## Share Three.js across bundles

Use `context.THREE`, as in
[`examples/spinning-cube/game.js`](../examples/spinning-cube/game.js). No engine
code is bundled into the game. Use the platform's loaders through
`context.runtime("addons/…")` instead of bundling them.

Game source that imports from `three` needs a build step that rewrites those
imports to `context.THREE` (for example, a module that exports
`let THREE; export const setThree = (value) => { THREE = value; }` called first in
`createGame`). Do not rewrite `three` to the URL `/runtime/three.js`: published
bundles load from the game origin, where that path does not exist. Bare package
names are not browser URLs. Do not package another engine copy, use a CDN, or
rely on an inline import map. Runtime upgrades require checking every game; they
upgrade together.

## Optional progress capability

The host provides `context.progress` with `version: 1` (the save format's own
version), and `context.launchReason` (`"open"` or `"restart"`). Keep the feature
check: the capability is absent if the player cannot prepare saving. The player selects progress before
calling `createGame`, and restart preserves long-term progress. A confirmed
**Reset progress** action is separate from restart.

```js
export async function createGame(context) {
  const progress = context.progress?.version === 1 ? context.progress : null;
  const saved = progress ? await progress.load() : { kind: "empty" };
  // Validate/migrate saved.snapshot before creating game resources or saving.
  // saved.kind is "saved", "empty", or "unavailable" (with a reason).
  // An unsupported schema must remain untouched; report the load failure.
  if (saved.kind === "unavailable") throw new Error("Progress unavailable");
  const state = saved.kind === "saved" ? validate(saved.snapshot) : initialState();
  // At meaningful checkpoints, capture plain JSON and handle rejected saves:
  async function checkpoint() {
    if (progress) await progress.save({ schemaVersion: 1, data: state });
  }
  // ...create the scene and input, invoke checkpoint during play...
  return {};
}
```

`load()` returns a copy of the snapshot selected at the paused launch boundary;
it never changes a running game's state from a late network response. Treat
`unavailable` separately from an absent save. `save()` captures its argument
immediately and resolves with `{sequence}` after the local transaction commits,
without a network request. Transfer status belongs to the player. Payloads are
versioned plain JSON, at most 64 KiB including the envelope, with finite numbers,
no cycles or prototype keys, and maximum nesting depth 32.

The platform owns the game ID, local profile partitions, account transfer,
and its temporary credentials. Bundles must not implement separate account/cookie
or storage logic. Save during play; a disposed/aborted game cannot submit a new
save. Already accepted local writes finish independently of game teardown.
When the capability is absent, play without persistence and communicate that
limitation.

## Integrate and release

1. Build/export ESM `game.js` with relative assets/chunks and a `game.json`
   manifest listing every runtime file.
2. Test the bundle in the local container with `npm run dev -- <id>`, including
   mobile/desktop, input, pause/resume, restart, loading failures, cleanup,
   options and console errors. `npm run verify -- --games=../fundev-games --game=<id>`
   runs the generic lifecycle checks on the game; it does not verify gameplay.
3. Follow [independent registration](game-registry.md) to upload the bundle and
   atomically update the R2 catalog. No website build/deployment is required.

Local builds bundle each `<id>/` of the games directory at `/games/<id>/<version>/`. Remote-origin
builds bundle no games and read the R2 catalog instead.

Keep game assets inside their bundle. Remote-origin builds permit the configured
game origin for scripts, fetches, images and media; default local builds permit
same-origin scripts, styles, and resources. Both disallow inline scripts/styles,
eval, data URLs and unrelated external assets. Only game pages (`/games/*`) also
allows `blob:` images and fetches, Blob URL workers and WebAssembly compilation
(`'wasm-unsafe-eval'`), which the glTF, Draco and KTX2 loaders need; the rest of
the site keeps workers same-origin for the service worker. Verify other loaders
under the preview's real headers before considering production-header changes.
Bundles execute as trusted same-origin code; this is a platform for the owner's
games, not a sandbox for untrusted third-party uploads.

The integration example is outside the games repository, so it is never published
implicitly. To try it locally, copy it to a temporary `<id>/` directory there with a
`game.json`, then remove that directory before publishing.
