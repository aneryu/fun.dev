# fun.dev game bundles — API v1

fun.dev owns the page and the Three.js runtime. A game delivers an ES module and
its assets. It does not create an HTML document, renderer, or animation loop.
The lobby and `/play/?game=<id>` player are shared across all games.

Apart from Three.js and this container API, games must be self-contained. Keep
game resources, UI copy, development tools and tests within their bundle.
Do not import platform application modules or rely on its CSS variables, global
resets, DOM IDs, catalog, router, storage or services. Draw game visuals and HUD in Three.js; the platform has no game UI API. Games do not create HTML
interfaces or ship CSS. Resolve game resources through `asset()`.
The Wooden Fish bundle demonstrates this boundary. Its source directory can be
copied and tested independently; only the foundation host needs replacing.

Optional `dev/`, `package.json` and `README.md` files at a bundle's root hold
development tooling and documentation. The static build omits these files;
runtime code must never reference them.

## Bundle layout

A game output directory can live anywhere; this layout is also used for local
preview fixtures. Independent publication adds a `game.json` file-list manifest.

```text
site/games/my-game/1.0.0/
  game.js             # ESM entry: export createGame(context)
  assets/             # optional textures, models, audio, etc.
  chunks/             # optional relative ESM imports
```

The public registry is R2's `games.json`, updated by the independent publisher
described in [game registration](game-registry.md). `site/games.json` is only a
local preview fixture. Array order is display order; remote entries additionally
include a `release` content hash generated by the publisher:

```json
[
  {
    "id": "my-game",
    "version": "1.0.0",
    "apiVersion": 1,
    "title": { "zh": "我的小游戏", "en": "My game" },
    "description": { "zh": "一句话说明玩法。", "en": "A short description." },
    "category": { "zh": "益智", "en": "Puzzle" },
    "platforms": ["mobile", "desktop"]
  }
]
```

IDs use lowercase ASCII letters, numbers, and single hyphens. Versions use
`major.minor.patch`. `platforms` lists devices the game actually supports: do
not mark a keyboard-only game as mobile. The catalog only lists ready games;
an empty array is valid. Unknown API versions and duplicate IDs fail validation.

`title`, `description`, and `category` accept either a shared string (e.g. `Demo`)
or an object containing both `zh` and `en` translations. Search matches both
languages. The published `cyber-muyu` bundle is a complete bilingual example,
including procedurally synthesized audio and audio cleanup on pause/disposal.

The player resolves the entry to `/games/<id>/<version>/game.js`. Asset paths
are relative to this bundle, never to the player's `/play/` URL. Keep published
version directories immutable and bump `version` when changing code or assets.

## Game interface

```js
export function createGame(context) {
  // Set up the scene and input. This function may also be async.
  return {
    update(delta, elapsed) {},
    resize({ width, height, pixelRatio }) {},
    pause() {},
    resume() {},
    localeChanged(locale) {},
    dispose() {},
  };
}
```

`createGame` must return an object. All hooks are optional, synchronous methods.
The module's top level must not start gameplay or allocate per-session resources:
ES modules are cached; restarting calls `createGame` again with a fresh context.

| Context | Ownership and behavior |
| --- | --- |
| `apiVersion` | Currently `1`. |
| `locale` | Live `zh` or `en` getter. Read to select game UI text. |
| `THREE` | Platform's shared Three.js module, pinned to `0.186.1`. |
| `scene` | Fresh scene owned by the container. Add game objects here. |
| `camera` | Default perspective camera at `(0, 0, 5)`, looking toward the origin. |
| `setCamera(camera)` | Replace the active camera, e.g. with an orthographic camera for a 2D game. |
| `renderer` | Shared host renderer for this session. Configure as needed; do not dispose it or replace its loop. |
| `canvas` | Focusable canvas. Bind pointer/keyboard input here; preserve Tab navigation. |
| `viewport` | Live `{ width, height, pixelRatio }` values, in CSS pixels; DPR capped at 1.5 on mobile/compact screens and 2 on desktop. Treat as read-only. |
| `invalidate()` | Request a frame for an on-demand game after input or an asynchronous scene change. |
| `asset(path)` | Resolves a path inside this versioned bundle, e.g. `asset('assets/ball.webp')`. |
| `signal` | Aborted when leaving, restarting, timing out, or failing. Use for fetches and DOM listeners. |
| `track(resource)` | Registers a resource with `dispose()`, returns it, disposes it once at teardown. |
| `onCleanup(fn)` | Registers synchronous cleanup for timers, audio, custom objects, etc. |
| `progress` | Optional v1 local-save capability; see below. |
| `launchReason` | `"open"` or `"restart"`; reset is an explicit player action. |
| `reducedMotion` | User's reduced-motion preference at session creation. Avoid decorative motion when true. |

The host calls `localeChanged` and `resize` after creation, then `resume` (or `pause` if hidden),
then `update` before each render. `delta` and `elapsed` are **seconds**; delta
is clamped to 0.05, and elapsed is accumulated simulation time. A resume starts
with delta 0. Hidden tabs and manual pause stop the render loop; becoming visible
does not override a manual pause. The game surface is inert while paused or
loading so its controls cannot take keyboard focus. `pause`/`resume` must also suspend/resume the
game's own audio and non-render activity. A resize may draw a still frame while
paused. Orthographic camera bounds belong to the game and should be updated in
`resize`; the host updates perspective camera aspect ratios automatically.

`localeChanged(locale)` also runs when the player switches languages. Update
game labels without recreating the session or resetting progress. The callback
is optional for existing bundles; the host always translates its own controls.

One frame loop calls `update` and then `renderer.render(scene, camera)`. Do not
start a second loop or call `renderer.render()` from `update`. Postprocessing
pipelines and multiple viewports are outside API v1; extend the contract before
adding games that need them.

Games run continuously by default. For games that can rest between interactions,
return `renderMode: "on-demand"`. Call `context.invalidate()` when input changes
the scene, and return `true` from `update` while an animation needs more frames.
Otherwise the host renders that frame and stops until the next invalidation.
Idle time does not advance simulation time. Resize still draws a frame.

Design games for touch first. The mobile player fills the available viewport,
with platform controls in a modal menu that pauses gameplay. Keep HUD controls
clear of the top-left menu and leave generous margins around screen edges.
Verify portrait and landscape, cap geometry and texture costs, and stop work
while paused. Do not require browser fullscreen support to make the game usable.

## Resource cleanup

Register resources **as they are created**, including before an `await`:

```js
export async function createGame({ THREE, scene, track, asset, signal, onCleanup }) {
  const geometry = track(new THREE.BoxGeometry());
  const material = track(new THREE.MeshBasicMaterial({ color: 0xffd43b }));
  const mesh = new THREE.Mesh(geometry, material);
  scene.add(mesh);

  const response = await fetch(asset('assets/level.json'), { signal });
  if (!response.ok) throw new Error('Level unavailable');
  const level = await response.json();
  signal.throwIfAborted();
  // Use level to initialize gameplay.

  return { dispose() { scene.remove(mesh); } };
}
```

At teardown the host stops frames, aborts `signal`, runs `dispose`, then runs
registered cleanups in reverse order, removes the surface, and releases its
renderer. A failing cleanup does not prevent later cleanups. Resources registered
after cancellation are disposed immediately. If async creation finishes late,
its returned `dispose` still runs. Check `signal` after awaits to avoid starting
new activity in a cancelled game. Creation has a 30-second timeout.

`track` geometry, materials, textures, render targets, controls, and skeletons
separately when applicable. Do not also dispose tracked resources in `dispose`.
Use `onCleanup` for untracked timers/listeners and closing `ImageBitmap` objects;
resources removed from a scene are still the game's responsibility. See the
[Three.js disposal guide](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).

Input listeners should use `{ signal }`. Keep game keyboard handling on the
canvas, not global keys that block platform controls. The game owns its HUD
geometry, hit testing, keyboard controls and accessible canvas labels.
Camera-attached meshes can draw screen-space HUD in the same render pass;
use depthTest/depthWrite false and explicit renderOrder for overlay materials.
Audio starts after a user gesture.

## Share Three.js across bundles

The simplest bundle uses `context.THREE`, as in
[`examples/spinning-cube/game.js`](../examples/spinning-cube/game.js). No engine
code is bundled into the game.

For source code or addons that import from `three`, configure the game's bundler
to externalize `three` and rewrite that import to `/runtime/three.js`. For
example, a Rollup-based build uses:

```js
{
  external: ['three'],
  output: {
    format: 'es',
    entryFileNames: 'game.js',
    paths: { three: '/runtime/three.js' }
  }
}
```

Bundle any used addons into the game with the **same** Three.js version, leaving
their core `three` imports external too. Bare package names are not browser URLs.
Do not package another engine copy, use a CDN, or rely on an inline import map.
The platform exports its core through `/runtime/three.js`; both it and the host
resolve to one browser module. Runtime upgrades require checking existing games;
breaking contract changes require a new API version.

## Optional progress capability

API v1 hosts may provide `context.progress` with `version: 1`, and
`context.launchReason` (`"open"` or `"restart"`). Feature-detect the capability;
older hosts and bundles remain compatible. The player selects progress before
calling `createGame`, and restart preserves long-term progress. A confirmed
**Reset progress** action is separate from restart.

```js
export async function createGame(context) {
  const progress = context.progress?.version === 1 ? context.progress : null;
  const saved = progress ? await progress.load() : { kind: "empty" };
  // Validate/migrate saved.snapshot before creating game resources or saving.
  // saved.kind is "saved", "empty", or "unavailable" (with a reason).
  // An unsupported schema must remain untouched; report the load failure.
  if (saved.kind === "unavailable") throw new Error("Progress unavailable");
  const state = saved.kind === "saved" ? validate(saved.snapshot) : initialState();
  // At meaningful checkpoints, capture plain JSON and handle rejected saves:
  async function checkpoint() {
    if (progress) await progress.save({ schemaVersion: 1, data: state });
  }
  // ...create the scene and input, invoke checkpoint during play...
  return {};
}
```

`load()` returns a copy of the snapshot selected at the paused launch boundary;
it never changes a running game's state from a late network response. Treat
`unavailable` separately from an absent save. `save()` captures its argument
immediately and resolves with `{sequence}` after the local transaction commits,
without a network request. Transfer status belongs to the player. Payloads are
versioned plain JSON, at most 64 KiB including the envelope, with finite numbers,
no cycles or prototype keys, and maximum nesting depth 32.

The platform owns the game ID, local profile partitions, account transfer,
and its temporary credentials. Bundles must not implement separate account/cookie
or storage logic. Save during play; a disposed/aborted game cannot submit a new
save. Already accepted local writes finish independently of game teardown.
When the capability is absent, play without persistence and communicate that
limitation. See Wooden Fish 1.1.0 for a complete checkpoint example.

## Integrate and release

1. Build/export ESM `game.js` with relative assets/chunks and a `game.json`
   manifest listing every runtime file.
2. Test the bundle in a local container, including mobile/desktop, input,
   pause/resume, restart, loading failures, cleanup and console errors.
3. Follow [independent registration](game-registry.md) to upload the bundle and
   atomically update the R2 catalog. No website build/deployment is required.

For local preview only, copy a bundle to `site/games/<id>/<version>/` and add it
to `site/games.json`. These local fixtures are excluded from remote-origin builds.

Keep game assets inside their bundle. Remote-origin builds permit the configured
game origin for scripts, fetches, images and media; default local builds permit
same-origin scripts, styles, and resources. Both disallow inline scripts/styles, eval, unrelated external assets,
and data/blob URLs. Some loaders, embedded GLB textures, workers, WASM, and audio
implementations need additional policies; verify the specific game under the
preview's real headers before considering scoped production-header changes.
Bundles execute as trusted same-origin code; this is a platform for the owner's
games, not a sandbox for untrusted third-party uploads.

The integration example is outside `site/`, so it is never published implicitly.
To try it locally, copy it to a temporary game version directory and add a local
catalog entry, then undo those local registrations before publishing.
